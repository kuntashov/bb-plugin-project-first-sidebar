# 03 — Обновлять индекс при изменениях истории и каталога

**Что сделать:** новые принятые запуски и изменение видимости отражаются в открытых окнах без перезагрузки, включая изменения, пришедшие во время чтения каталога. [Спецификация](../thread-execution-highlighting-spec.md): Catalogue, jobs and concurrency; Client contract.

**Блокируется:** 02 — Заполнить индекс всех видимых тредов в фоне.

**Статус:** ready-for-agent после устранения блокировок и сверки спецификации.

- [ ] До сверки зарегистрированы обработчики истории, одна общая серверная подписка `thread:changed` и `realtime:connection`; готовность соединения обеспечена до baseline либо каталог повторно сверяется после первого connected. Изменения доставляются клиентам через invalidation ID; обновление одной проекции перерисовывает строку даже без изменения title/status/updatedAt.
- [ ] Уведомления об истории объединяются на ID; dirty revision и generation ограждают запись, при событии во время чтения выполняется повторная сверка. При доказанно неизменном accepted нет повторного чтения requested и лишней invalidation; та же identity после изменения истории не считается доказательством неизменности.
- [ ] При title/visibility change ID проверяется через публичный каталог с includeHidden:false: успешное исключение удаляет его из manifest и поколений и инвалидирует token, ошибка запроса не удаляет. Во время снимка фиксируются изменённые ID и повторно проверяются, чтобы старый снимок не вернул скрытый и не потерял добавленный тред.
- [ ] Тесты покрывают lower surviving accepted и очистку истории, новый accepted, hidden↔visible без output, обе гонки snapshot, повторное событие во время чтения и клиентское обновление без иных изменений строки. Fork получает результат после успешного фонового чтения своей скопированной истории без нового запуска, независимо от дальнейших изменений источника; обычный child не наследует конфигурацию.

## Граница уведомлений BB 0.48.1

По исследованию @thread:thr_q3iqmcy5yp, отдельный `history-compacted` доставляется только подписчикам конкретного треда и не поступает в общую подписку. Проверенные в исходниках BB 0.48.1 операции чистой компакции не выбирают события `turn/input/accepted` и `client/turn/requested`; в изолированном runtime удаление синтетического retained output оставило последний accepted неизменным. Отдельные подписки на каждый ID не добавляются. Это свидетельство относится к проверенной версии и операциям, а не ко всем возможным изменениям истории.

Успешный edit по исходникам транзакционно удаляет заменяемый суффикс и записывает новый requested, затем отправляет `events-appended` и `history-rewritten`. При ошибке после commit ветка обработки уже записанной операции может не повторить уведомление. Если соединение остаётся открытым и новый триггер не приходит, обнаружение такого пропуска не гарантируется. Полная сверка при startup и reconnect восстанавливает данные при успешном чтении; полноценное resume предусмотрено в ticket 05. Edit с отклонённой заменой не воспроизведён в изолированном runtime, поэтому его поведенческая приёмка остаётся открытой.

Публичная схема допускает `thread:changed` без `id`, а клиент SDK доставляет такое сообщение общей подписке. Просмотренный `notifyThread` в BB 0.48.1 формирует сообщение с ID; отправку сообщения без ID в работающем runtime не наблюдали. Для допустимого сообщения без ID об изменении состава или истории плагин запускает общую сверку каталога и истории и инвалидирует незавершённые чтения. Пока состав каталога и история конкретного ID не сверены, прежняя проекция отображается как unverified, в том числе при ошибке запроса каталога; после перезапуска действует обычная проверка startup. Для `events-appended` сверка нужна при неизвестных типах либо наличии accepted/requested; явные типы другого вывода и изменения статуса или pin её не запускают. Это событийный путь, а не polling.
